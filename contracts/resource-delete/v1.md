# Guarded resource deletion contract

This is the feature-specific consumer contract for explicit product-native
deletion. It uses the landed native boundary; defaults and frozen native-v1
remain unchanged. Source integration is prepared, with delivery validation
pending. This document does not claim complete parity or live-operation authority.
Reference: `gh-axi` `2bffd9a5b60ded64d6c9851683b27a480173a7ee`, the delete handlers
in `src/commands/{issue,run,release,label,gist}.ts`. Reference implicit `--yes`
behavior is deliberately not copied.

## Selection and authority

Every new leaf requires `--auth-source native`, explicit `--hostname`, exact
`--expected-url`, and an operation-specific confirmation whose value equals that
URL. Project leaves additionally require `--repo` and
`--expected-project-id`. Numeric identifiers use canonical positive decimal.
No default project, implicit confirmation, generic `--yes`, batch, or fallback
is accepted. The entire operation uses one shared native client, credential and
configured host/API/web mapping; it never queries an official profile.

Leaf-specific contracts:

| Leaf | Additional caller expectations | Destructive opt-in |
| --- | --- | --- |
| `issue delete IID` | `--expected-id GLOBAL_ID`, `--expected-state`, `--expected-updated-at` | `--confirm-delete-issue URL` |
| `pipeline delete ID` | `--expected-sha`, `--expected-ref`, `--expected-status`, `--expected-updated-at` | `--confirm-delete-pipeline URL` and separate `--acknowledge-child-cancellation URL` |
| `release delete TAG` | `--expected-commit`, `--expected-created-at` | `--confirm-delete-release URL` and separate `--acknowledge-catalog-unpublication URL` |
| `snippet delete ID` | `--expected-author-id`, `--expected-updated-at`; personal only, no repo accepted | `--confirm-delete-snippet URL` |
| `snippet delete-project ID` | `--expected-author-id`, `--expected-updated-at`; exact project required | `--confirm-delete-snippet URL` |

Pipeline deletion requires both confirmations to equal the exact parent
`--expected-url` on every invocation. The child-cancellation acknowledgment is
never inferred from native auth, parent confirmation, environment, configuration,
parent status or a child snapshot. Missing or mismatched acknowledgment refuses
before credential or provider access. It acknowledges possible cancellation of
surviving child pipelines and their jobs, even if parent deletion later fails;
it does not authorize separate child deletion or cancellation requests.

Release deletion requires both confirmations to equal the exact release
`--expected-url` on every invocation. The catalog-unpublication acknowledgment
is never inferred from native auth, release confirmation, environment,
configuration, catalog state or version count. Missing or mismatched
acknowledgment refuses before credential or provider access. It acknowledges
possible unpublication of the project's surviving CI/CD Catalog resource when
the last catalog version is removed; it grants no separate catalog mutation
authority and does not replace any exact project, release or retained-tag guard.

Personal and project snippets are separate leaves so the shared static auth
selector can require a project on every project leaf and forbid it on a
personal leaf. No new auth parser is needed. A personal snippet must have a
null `project_id`; a project snippet must match the selected numeric project.
All returned URLs must match the configured web authority, including its base
path, not an assumed `https://<logical-host>` origin. Release tags containing
percent characters are refused by the bounded native route contract rather than
reinterpreted. Native persisted-config/self-managed mapping on Windows remains
unproven; this increment does not broaden that authentication contract.

## Provider semantics and evidence

GitLab REST v4 evidence is pinned to release `v19.4.0-ee`, source
`fa703f93afaf1133cd263f6aa0e91d284d7f1ebf`. The source-backed route contract is
not a claim that a live server or every historical version was tested.

Base source URL:
https://gitlab.com/gitlab-org/gitlab/-/tree/fa703f93afaf1133cd263f6aa0e91d284d7f1ebf

| Resource | Fixed DELETE route | Acknowledgment | Authoritative source |
| --- | --- | --- | --- |
| Issue | `projects/PROJECT_ID/issues/IID` | 204 | `lib/api/issues.rb`, `doc/api/issues.md` |
| Pipeline | `projects/PROJECT_ID/pipelines/ID` | 204 | `lib/api/ci/pipelines.rb`, `doc/api/pipelines.md` |
| Release | `projects/PROJECT_ID/releases/ESCAPED_TAG` | 200 with exact deleted release entity | `lib/api/releases.rb`, `doc/api/releases/_index.md` |
| Personal snippet | `snippets/ID` | 204 | `lib/api/snippets.rb`, `doc/api/snippets.md` |
| Project snippet | `projects/PROJECT_ID/snippets/ID` | 204 | `lib/api/project_snippets.rb`, `doc/api/project_snippets.md` |

Project path discovery must prove numeric ID, full namespace path and web URL.
Subsequent project-resource requests use that bound numeric project ID. Resource
GETs establish identity and expected state, with a final recheck before the
single DELETE. Source `lib/api/helpers.rb` checks `If-Unmodified-Since` separately
from destruction on some routes; it is not a universal atomic CAS and this
contract does not advertise one.

Consequences are resource-specific:

- Pipeline deletion expires caches and removes immediately related builds,
  logs, artifacts and triggers. It is not job erasure and does not recursively
  delete child pipelines. The pinned
  [destroy service](https://gitlab.com/gitlab-org/gitlab/-/raw/fa703f93afaf1133cd263f6aa0e91d284d7f1ebf/app/services/ci/destroy_pipeline_service.rb)
  cancels cancelable jobs before removal with cascading cancellation enabled;
  the [cancellation service](https://gitlab.com/gitlab-org/gitlab/-/raw/fa703f93afaf1133cd263f6aa0e91d284d7f1ebf/app/services/ci/cancel_pipeline_service.rb)
  can cancel surviving child pipelines and their jobs. This effect may precede
  failed parent deletion. No job or downstream-pipeline mutation route is sent
  by the client; these are provider effects of the single parent DELETE. An
  observed terminal status or absence of children is not an atomic guarantee
  against such effects, so no snapshot waives the separate acknowledgment.
- Release deletion removes the release and retains its tag. The pinned
  [release destroy service](https://gitlab.com/gitlab-org/gitlab/-/raw/fa703f93afaf1133cd263f6aa0e91d284d7f1ebf/app/services/releases/destroy_service.rb)
  also marks the project's surviving CI/CD Catalog resource unpublished when
  no catalog versions remain. Catalog unpublication may have occurred even
  after an ambiguous response. No catalog-state or version-count snapshot
  atomically excludes this effect, so none waives the separate acknowledgment.
  Read the exact tag/commit before and after; never send repository tag deletion,
  separate catalog mutation or local Git cleanup.
- Snippet deletion removes the selected snippet and its provider-managed
  content. Personal and project ownership must never be inferred interchangeably.
- Issue deletion is not close/reopen and exposes no undelete guarantee.

## Outcome and concurrency rules

Exactly one intended DELETE; no automatic redirect or retry, even to the same
origin. Tight per-response and operation byte/time bounds remain shared and
feature-enforced. These are fixed-resource operations, not paginated enumerations.
No returned Link, Location, sibling URL or unexpected identifier grants authority.

A successful receipt requires exact preflight identity, the route's expected
acknowledgment, and bounded readback supporting absence while the selected
parent/account remains accessible. A release success also verifies the tag was
retained at the expected commit. Do not turn an initial 404 into
`already_deleted`: private-resource invisibility cannot prove historical deletion.
An unexpected response, lost connection, timeout or malformed response remains
ambiguous unless sufficient exact response evidence is present. In particular,
404 after a failed DELETE does not prove the request deleted anything. A 401,
403, network failure or unreadable response is never substituted for 404.
Reconciliation only reads and is bounded; it cannot issue a second DELETE.

The receipt distinguishes provider acknowledgment from an observed postcondition.
`delete_attempted` records one client invocation, not guaranteed provider receipt.
`expected` retains the matched state/revision, pipeline ref/commit/status, release
creation/commit, or snippet author/revision alongside the exact numeric identity.
`intended_effects` describes the operation, not measured effects after an error.
Pipeline receipts include `may_cancel_surviving_child_pipelines` among these
effects and `child_cancellation.acknowledged=true` for the distinct caller
acknowledgment, separately from the DELETE response's `acknowledged` field.
`child_cancellation.outcome` is `not_attempted` only before DELETE invocation and
`unverified` after any attempt, including successful, rejected and ambiguous
parent outcomes. Parent absence never proves child cancellation or its absence;
no child state, count or atomic absence-of-effects guarantee is reported.
Release receipts include `delete_release`, `may_unpublish_catalog_resource` and
`retain_tag` as intended effects. `catalog_unpublication.acknowledged=true`
records the distinct caller acknowledgment separately from the DELETE response's
`acknowledged` field. `catalog_unpublication.outcome` is `not_attempted` only
before DELETE invocation and `unverified` after any attempt, including successful,
rejected and ambiguous release outcomes. Release absence and retained-tag
readback do not establish catalog unpublication or its absence. No catalog state,
version count or atomic absence-of-effects guarantee is reported.
After the first exact preflight, errors carry the bounded receipt with action
`not_applied` (no DELETE invocation), `rejected` (recognized HTTP rejection), or
`ambiguous`; all are non-retryable. Initial 404 has no observed resource identity
and remains an ordinary not-found failure, never an `already_deleted` action.
Errors do not expose provider response text or credentials. Successful data uses
`deletion.action=deleted`, the exact resource/scope/URL, `delete_status`, and
`postcondition=not_found`; backend is `native` with no official upstream version.
`ambiguous_delete` exits 6 and must not invite blind retry. The mutation and
readback each have a 10-second cap within the 45-second outer native lifetime;
responses are capped at 2 MiB and the native aggregate bound remains 8 MiB.
There are at most 11 fixed-route requests for a release and fewer for other
resources, with no pages, returned links, sleeps or polling. Preflight and postcondition observation are best-effort, not atomic with
concurrent updates, permission changes or tag/release recreation.

## Explicit residual: label deletion cannot meet numeric identity confinement

Label deletion is an accepted temporary parity gap and remains disabled and
undelivered, not silently retired. The independently supported resources continue.
The resource-specific blocker is independent of the resolved transport choice.

At the pinned source:

- `lib/api/labels.rb` exposes `DELETE projects/:id/labels/:name` and the deprecated
  `DELETE projects/:id/labels` with typed `label_id` or `name` parameters.
- Both call `API::Helpers::LabelHelpers#delete_label`.
- `lib/api/helpers/label_helpers.rb`, lines 33-40 and 110-119, resolves
  `labels.find_by_id(id_or_title) || labels.find_by_title(id_or_title)`.
- Both routes therefore fall back from a missing numeric ID to a label **title**.
  The deprecated integer `label_id` does not provide an ID-only delete operation.

A final preflight can prove label ID 42 and its expected name. If another actor
removes it before DELETE, a distinct existing project label named `42` becomes
the fallback target. `include_ancestor_groups=false` prevents inherited-group
selection but does not prevent that project-label collision. The timestamp
helper compares time, not expected label ID; an older colliding label can pass
it. A preliminary catalog or collision scan cannot close the intervening race.
Label removal also affects its associations across issues/MRs and cannot be
represented as merely removing one issue's label.

Do not expose a stub, unsafe numeric/name alias, or permanent exclusion claim.
Deliver the independent supported resource pieces and report this exact residual.
Revisit only with a proven ID-exclusive/provider-enforced expected-ID mutation
capability that satisfies the no-label-name-collision constraint. Weakening the
targeting guarantee or patching the provider is not part of this increment.

## Prepared executable evidence

`internal/product/resource_delete_native_test.go` drives the product CLI entry
with isolated TLS servers and runtime dependencies. It prepares success,
confirmation/selector refusal, identity drift, permission/absence ambiguity,
malformed/bounded responses, exact request count, same-origin and cross-origin
redirect, native-unavailable/no-fallback and cancellation cases. A project/API/web
base-path mapping different from the logical hostname is intentional.

The pre-integration issue success test returned the old `security_boundary`;
the original delegated 307/308 TLS probe separately reproduced an unintended
second DELETE. `internal/delegate/glab/delete_transport_test.go` now retains that
pinned unsafe behavior as a diagnostic, not a claim that upstream was fixed.
The native tests require zero redirected requests.

`resource_delete_e2e_test.go` prepares compiled canonical/alias TLS coverage;
`resource_delete_guards_test.go` covers exact expectation mismatches and the
remaining disabled operations. `resource_delete_pipeline_test.go` covers default
and mismatched child-cancellation refusal, separate exact-parent confirmation,
per-invocation scope, opt-in provider effects, preflight drift and ambiguous
outcomes after child cancellation. `resource_delete_release_test.go` covers
default and mismatched catalog-unpublication refusal, separate release
confirmation, per-invocation scope, last-version and remaining-version effects,
retained-tag guards, preflight drift and ambiguous outcomes after unpublication.
These synthetic controls do not establish
live-provider behavior. Full feature validation and race/vet remain explicit
delivery gates.
